# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A WordPress site for "Bishkek Park" (a shopping mall), run locally via Local (Local by Flywheel/WP Engine). The repo root is the Local site folder; the actual web root is `app/public/`. WordPress core, the `polylang` plugin, and all default files are committed as-is — **all real development happens in the custom theme**:

```
app/public/wp-content/themes/bishkek-park/
```

Do not edit files under `wp-admin/`, `wp-includes/`, or other core paths — they are vendored WordPress core, not project code.

## Environment

- No build step: plain PHP + hand-written CSS/JS, no npm/webpack/vite/composer anywhere in the theme. Edit the CSS/JS files directly; there is nothing to compile.
- `app/.envrc` is auto-generated by Local on site start (direnv) and points at Local's bundled MySQL/PHP/wp-cli/composer binaries and config paths. Don't hand-edit it; if it looks wrong, restart the site in the Local app to regenerate it.
- PHP 8.2, WP-CLI available via the paths `.envrc` sets up (only useful if the Local site is currently running).
- There is no test suite, linter config, or CI in this repo. Verify changes by running the site through the Local app and checking the page in a browser.

## Theme architecture

- `functions.php` — theme bootstrap: defines `BISHKEK_PARK_*` constants, requires the `inc/` files, registers the nav menu, and enqueues styles/scripts. `assets/js/front-page.js` is only enqueued when `is_front_page()`. `assets/css/front-page.css` is enqueued on `is_front_page()`, the `bp_shop` archive, **and** the single `bp_shop` page, since it owns the shared `.bp-shops-grid`/`.bp-shop-card` styles all three reuse; `assets/css/shop-catalog.css` + `assets/js/shop-catalog.js` are catalog-page-only (`is_post_type_archive( 'bp_shop' )`, the floor-filter UI), and `assets/css/shop-single.css` is single-shop-page-only (`is_singular( 'bp_shop' )`, the detail layout).
- `inc/post-types.php` — registers three custom post types that back the editable homepage sections: `bp_shop` (Магазины), `bp_event` (Мероприятия), `bp_banner` (Баннеры, the hero slider). (There is no `bp_movie` CPT — Синематика has no wp-admin editing at all; its homepage section is populated live from the Cinematica.kg API, see `inc/cinematica-api.php`/`inc/cinematica-settings.php` below.) Each is REST-enabled with `title`, `thumbnail`, `page-attributes` support; ordering is via `menu_order`. `bp_shop` also has `has_archive` enabled: its archive is the full shop catalog (all shops, one page, filterable by floor client-side) linked from the homepage shops section's "Все магазины" link; `bishkek_park_shop_catalog_query()` (in this file, hooked to `pre_get_posts`) makes that archive's main query show every shop ordered by `menu_order` instead of WordPress' default paged loop. The single shop page shows image, `_bp_description`, `_bp_hours`/`_bp_website` (each falling back to a default translatable string — "Пн - Вс: 10:00 - 22:00" / "info@bishkekpark.kg" — when empty), a back link to the catalog, and a "Магазины на этаже" `bp-shops-grid` of other shops sharing the same `_bp_floor` value (hidden if the current shop has no floor set). Both templates live in `template-parts/shop/` (not the theme root — see that section below) and are wired up via the `archive_template`/`single_template` filters (`bishkek_park_shop_archive_template()`/`bishkek_park_shop_single_template()`) also defined in this file. `_bp_floor` is stored as a bare value (e.g. `"2"`, entered as just `2` in wp-admin) — `bishkek_park_sanitize_shop_floor()` (also here) strips a leading "Этаж" on save in case someone types the old style, and `bishkek_park_get_shop_floor_label()` (functions.php) is the single place that formats it into the displayed "Этаж 2" label; always use that helper rather than echoing `_bp_floor` directly, and use the raw meta value (not the label) for filter/`meta_query` matching.
- `inc/meta-boxes.php` — one data-driven meta box implementation shared by `bp_shop`, `bp_cafe`, `bp_event`, `bp_banner`, and `page` (no `bp_movie` entry — see above). Field definitions per post type (meta key, label, description, optionally `max_length` and `sanitize_callback`) live in `bishkek_park_meta_fields()`; add a field there rather than writing new render/save boilerplate. `bp_shop` fields: `_bp_category`, `_bp_floor`, `_bp_description` (max 400 chars), `_bp_hours`, `_bp_website`.
- `inc/cinematica-settings.php` — a top-level "Синематика" admin menu page (`manage_options`, slug `bishkek-park-cinematica`, reusing the `dashicons-tickets-alt` icon the old `bp_movie` CPT menu used) with two plain-URL settings, both optional and falling back to the current Bishkek Park hall (ID 3) defaults when blank: `bishkek_park_cinematica_api_url` (read via `bishkek_park_get_cinematica_api_url()`) and `bishkek_park_cinematica_link_url` (read via `bishkek_park_get_cinematica_link_url()`). Registered with the Settings API (`register_setting`/`settings_fields`, sanitized with `esc_url_raw`) so editing them doesn't need any custom nonce handling. Exists so the cinema hall's ID can be updated from wp-admin if Cinematica.kg ever changes it, without a code deploy.
- `inc/cinematica-api.php` — `bishkek_park_get_cinematica_sessions()` fetches today's showtimes from `bishkek_park_get_cinematica_api_url()` (see `inc/cinematica-settings.php` above), filters to entries whose `date` matches `current_time( 'd.m.y' )` and excludes any with `is_disabled`/`disable_sales` truthy, groups the rest by `movie_id` into `title`/`poster` (absolute URL)/`times` (deduped, chronological), and sorts movies by earliest showtime. A WP-Cron job (`bishkek_park_refresh_cinematica_sessions`, scheduled on `init` via the `wp_next_scheduled()` guard pattern since themes have no reliable activation hook) re-fetches and re-caches this every 10 minutes so a real visitor's page load never pays the API's latency directly; the transient itself is kept 1 hour as a safety net, and both the cron job and the on-demand getter leave the previous same-day cache in place on a failed fetch rather than blanking the section. This is what `template-parts/homepage/cinema.php` renders, linking each card (and the header's "Синематика" nav item) out to `bishkek_park_get_cinematica_link_url()` since there's no single-movie page on this site.
- `inc/translatable-strings.php` — every hardcoded UI string (nav labels, footer text, homepage copy) is centralized in `bishkek_park_translatable_strings()` and registered with Polylang via `pll_register_string()` so it's editable from Languages → String translations. Templates print these with `pll_e()` / `pll_esc_html_e()` / `pll_esc_attr_e()`, which this file also defines as safe-echo fallbacks so templates don't fatal if Polylang is deactivated. **When adding new UI copy: add the string to this file's array first, then reference it in the template with the `pll_*` helpers** — don't hardcode new strings directly into template-parts.
- `front-page.php` — the static front page is assembled purely by sequencing `get_template_part()` calls into `template-parts/homepage/*`. Section order there is the section order on the page.
- `template-parts/homepage/*.php` — each file is one homepage section. Sections backed by a CPT (`shops.php`, `events.php`) run their own `WP_Query`, `return` early if empty, and render a static grid that becomes a horizontally-scrollable slider (`bp-*-grid--slider` + `data-bp-slider-nav`) once post count exceeds a per-section "per row" constant (e.g. `BISHKEK_PARK_SHOPS_PER_ROW`). `cinema.php` follows the same return-early/grid/slider shape but its data comes from `bishkek_park_get_cinematica_sessions()` (see `inc/cinematica-api.php`) instead of a `WP_Query`. Slider prev/next behavior is generic — driven entirely by `data-bp-slider-nav`/`data-bp-slider-prev`/`data-bp-slider-next` attributes and handled by `assets/js/front-page.js`, so new sliders need no new JS.
- `hero.php` is the exception to the "return early if empty" rule: since it's the top of the page it always renders something. If `bp_banner` posts exist it renders one `.bp-hero__slide` per post (title/`_bp_badge`/`_bp_text`/`_bp_button_label`+`_bp_button_url`/featured image) with click-through `.bp-hero__dot` navigation (`data-bp-hero-slider` in the markup, click handling in `front-page.js`, only wired up when there are 2+ slides); with zero `bp_banner` posts it falls back to a single hardcoded slide (the original static hero copy/image) so the homepage never ships an empty hero.
- `template-parts/shop/archive-bp_shop.php` and `template-parts/shop/single-bp_shop.php` — the bp_shop catalog and detail pages, grouped in their own folder the same way homepage sections live under `template-parts/homepage/` rather than the theme root. Unlike homepage sections these are full page templates (each calls `get_header()`/`get_footer()` itself), so WordPress' default template hierarchy — which only looks in the theme root for `archive-{post_type}.php`/`single-{post_type}.php` — is pointed here via the `archive_template`/`single_template` filters in `inc/post-types.php`. If you add another full-page template for a CPT, follow the same pattern: put it in a `template-parts/{something}/` folder and add a matching hierarchy filter, rather than dropping it in the theme root. **Every full-page template (anything that calls `get_header()`/`get_footer()` itself, as opposed to a homepage section) must include a back link** as the first thing inside `<main>`, using the shared `.bp-back-link-wrap` / `.bp-back-link` component (defined in `assets/css/front-page.css` since that stylesheet is already loaded on all `bp_shop` pages — see the single/archive templates for the markup pattern) linking to wherever makes sense for that page (the archive back-link goes to `home_url( '/' )`; the single-shop back-link goes to the catalog archive). Register the link text as a new key in `inc/translatable-strings.php` rather than hardcoding it.
- `template-parts/header/site-header.php` and `template-parts/footer/site-footer.php` hold the actual header/footer markup; `header.php`/`footer.php` are just the thin document-shell wrappers (`get_header()`/`get_footer()` entry points).
- `assets/js/header.js` handles the mobile nav toggle and the language-switcher dropdown (open/close, outside-click, Escape-to-close). Vanilla JS, IIFEs, no framework/dependencies anywhere in the theme.
- `assets/icons/*.svg` are referenced via `bishkek_park_icon_url()`; the logo specifically is inlined via `bishkek_park_get_logo_svg()` so its fill can follow `currentColor` in CSS.
- `style.css` defines the design-token custom properties (`--bp-pink`, `--bp-navy`, `--bp-radius-*`, etc.) at `:root` — reuse these instead of hardcoding colors/radii in new CSS.

## Conventions

- All theme functions/hooks are prefixed `bishkek_park_`; CSS classes are prefixed `bp-` (BEM-ish: `bp-shop-card__name`, `is-open`, `is-disabled` state modifiers).
- Text domain is `bishkek-park`; admin-facing labels (post type names, meta box fields) are in Russian since that's the site's admin language.
- Script/style versioning uses `filemtime()` on the enqueued file (not a hardcoded version string) for cache-busting during development.

## Version control

Git is initialized in the theme root. Commit before major structural
changes so /rewind + git provide a full safety net.

## Custom fields approach

This project intentionally does NOT use ACF or any custom-fields plugin.
All meta fields are hand-coded via the data-driven pattern in inc/meta-boxes.php.
Do not suggest installing ACF — extend the existing pattern instead.

## Polylang CPT translation

bp_shop, bp_event have translation support enabled via
Settings → Languages → Custom Post Types — each post can have RU/KY
translated versions linked as separate posts. bp_banner should be enabled
there too the same way once the site is up (it's not automatic just from
registering the CPT in code). There is no bp_movie CPT — Синематика has no
wp-admin content at all, see inc/cinematica-api.php.

**Any `WP_Query`/`pre_get_posts` over these CPTs must explicitly set
`'lang' => pll_default_language()`** (guarded with
`function_exists( 'pll_default_language' )`) instead of relying on
Polylang's automatic current-language filtering of the main query.
Polylang's default filtering silently excludes posts with no translation
in the language currently being viewed — untranslated shops/movies/events
just vanish instead of erroring. Query the default (RU) language as the
canonical list, then swap in each post's current-language translation
where one exists via `bishkek_park_get_localized_post_id()` (defined in
functions.php) — see `template-parts/homepage/shops.php` and
`bishkek_park_shop_catalog_query()` in `inc/post-types.php` for the
pattern. This bit a real bug: the `bp_shop` archive query originally
omitted `lang` and came back empty on the front end because of this exact
issue.

## SEO

There is no SEO plugin (no Yoast/RankMath) — don't suggest installing one
unless asked; extend the theme directly instead, the same way custom
fields and translations are hand-rolled here.

- `<title>` is already handled by `add_theme_support( 'title-tag' )` in
  `functions.php`. `inc/seo.php` (required from `functions.php`) hooks
  `wp_head` to print `<meta name="description">` on `is_singular( 'page' )`,
  reading it from the `_bp_seo_description` post meta field. That field is
  defined in `inc/meta-boxes.php`'s data-driven `page` entry (a `textarea`
  field, same mechanism as `_bp_category`/`_bp_floor`/etc. for the CPTs) and
  is editable from the normal Page edit screen. Reading → "Your homepage
  displays" is set to a static page, so the front page is a real `page`
  post and gets a description the same way as any other page — no special
  case needed. Open Graph / Twitter Card tags are still not implemented;
  add them the same way (a new `wp_head`-hooked function in `inc/seo.php`)
  if a task calls for them.
- Polylang outputs `hreflang` alternate-language tags automatically on
  `wp_head` once a page has linked translations — no theme code needed for
  that; just make sure new content types stay registered as translatable
  in Settings → Languages → Custom Post Types (see above).
- Keep one `<h1>` per page (hero.php owns it on the front page, index.php
  on archive/search) and don't introduce a second one.
- Icon/decorative `<img>` tags intentionally use `alt=""` (many already do,
  see e.g. `template-parts/homepage/leasing.php`) — that's correct, leave
  them empty. But meaningful content images (hero image, category images,
  shop/event photos) should get real, descriptive `alt` text; several
  currently have `alt=""` and should be filled in with real copy when
  touched, not left empty by default.
- There is no `robots.txt` or XML sitemap in the repo; WordPress serves a
  virtual default `robots.txt` and core's built-in `wp-sitemap.xml`. Don't
  assume a sitemap plugin is present.
